## 1. 选点分析：为什么是这个点

对主方案各环节做"Agent 增益 × 风险可控性"二维评估：

| 候选改进点 | Agent 增益 | 风险可控性 | 结论 |
|---|---|---|---|
| L2 实时功控环（毫秒~百毫秒级） | 低——LLM 推理延迟与不可验证性不匹配实时控制 | 低——直接碰空口，失败代价高 | ❌ 排除 |
| L3 意图编排层 | 无增量——主方案中已是 Agent 形态 | — | ❌ 排除 |
| 轨迹/干扰预测模型架构设计 | 低——离线一次性建模问题，AutoML 收益边际 | 高 | ❌ 排除 |
| 空域走廊规划器 | 中——MAPF 求解器已高效，Agent 只能做参数调优 | 中 | ⚠️ 次选 |
| **数字孪生与预测模型的持续校准（Sim2Real 闭环）** | **高——现状是阶段性人工操作，强依赖专家，漂移期间全系统精度衰减** | **高——不碰实时控制环，所有动作经孪生验证后才发布** | ✅ **选定** |

**核心论据**：

1. **它是全系统的"精度地基"**：干扰预测的 RMSE、MARL 策略的实网性能、空域管控的干扰围栏，全部依赖孪生底座的保真度。底座漂移 → 全链路同时退化。这是主方案风险表中影响面最大的一项。
2. **现状流程有明确缺陷可量化改进**：主方案 8.2 节的校准是"阶段性"的（采集→人工分析→重训→发布，专家驱动，周期以周计）。而漂移源是持续发生的：季节植被变化（2.4GHz 穿透损耗可变化 3–8dB）、新建建筑、基站工参变更（方位角/下倾角调整）、新机型动力学特性。**漂移发生到下次人工校准之间的窗口期，系统在用错误的地基做决策。**
3. **任务形态天然适合 Agent**：这是一个"检测 → 归因 → 规划 → 执行 → 验证 → 发布"的多步骤、需要工具调用和分支判断的工作流，每一步都有不确定性需要推理（漂移是数据问题还是环境真变了？该补采数据还是重训模型？），但又**不需要实时性**（小时级闭环可接受）——恰好落在 LLM Agent 的能力甜区。
4. **失败模式安全**：Agent 的所有产出（新校准模型）必须通过孪生内回归测试 + 金丝雀发布才生效，最坏情况是"校准没生效，维持现状"，不会引入比现状更差的风险。

## 2. 问题陈述

### 2.1 现状（主方案基线流程）

```
[一次性] Sionna RT 仿真生成 → 训练无线电地图/预测模型
[阶段性·人工] 路测采集 → 专家分析误差 → 迁移学习校准（AIRMap 式，20% 实测降误差至 ~5%）→ 人工评审 → 发布
```

### 2.2 缺陷

| # | 缺陷 | 后果 |
|---|---|---|
| D1 | 漂移检测靠人工巡检或事故触发，无系统性监控 | 漂移窗口期不可知，可达数周 |
| D2 | 误差归因靠专家经验（是植被？新楼？工参变更？测量噪声？） | 归因慢且不一致 |
| D3 | 补救数据采集无定向性（全域重新路测） | 采集成本高、周期长 |
| D4 | 校准-验证-发布流程手工串联 | 端到端周期以周计 |
| D5 | 坏例（预测严重失误的场景）未被系统性挖掘和回灌 | 同类错误反复出现 |
| D6 | 下游模块（MARL 策略、管控围栏）不感知底座置信度变化 | 用过期精度假设做决策 |

### 2.3 机会

把 D1–D6 整合为一个由 Agent 自主驱动的持续闭环，使校准从"周级人工项目"变成"小时级自主流程"。

## 3. 目标与非目标

### 3.1 目标（Goals）

- **G1 自主漂移检测**：持续比对预测值与实测回流（MDT/无人机遥测/频谱监测），多维度（空间分区 × 频段 × 高度层 × 时段）监控误差漂移，小时级发现显著漂移。
- **G2 自动归因**：对漂移做根因分类（环境变化 / 工参变更 / 数据质量 / 模型退化 / 新对象类型），给出置信度与证据链。
- **G3 定向修复**：按归因结果规划最小代价修复动作——定向数据采集任务、定向仿真数据生成（只对漂移区域重跑 Sionna RT）、增量校准训练、坏例回灌。
- **G4 自主验证与发布**：修复后的模型在孪生内通过回归测试集 + 影子对比，自动走金丝雀发布；不达标自动回滚并升级人工。
- **G5 置信度广播**：向下游（L1 预测服务、L2 决策层、L3 意图层）发布各空间分区的当前校准置信度，供下游自适应调整保守度。
- **G6 可解释审计**：每次闭环产出结构化报告（漂移证据 → 归因 → 动作 → 验证结果），全程可审计、可回放。

### 3.2 非目标（Non-Goals）

- **NG1** 不参与实时功控/避撞决策（那是 L2 的职责，时延域不同）；
- **NG2** 不自主修改模型架构或训练超参搜索空间之外的代码（不是 AutoML 系统）；
- **NG3** 不直接控制无人机执行采集任务——只生成采集任务工单，由 UTM/运维系统审批执行；
- **NG4** 初期不处理对抗性数据投毒检测（列入远期）。

## 4. Agent 总体设计

### 4.1 设计范式：LLM 规划 + 确定性工作流混合（Plan-and-Execute over Workflow）

不采用纯自由 ReAct（步骤过长、易漂移），也不采用纯固定 pipeline（丧失归因推理能力）。采用**骨架固定、节点智能**的混合范式：

- **骨架**：六阶段工作流（监控→归因→规划→执行→验证→发布）由确定性状态机驱动，保证流程可预测、可审计；
- **节点**：归因、修复规划两个高不确定性节点由 LLM Agent 推理（ReAct + 工具调用），其余节点为确定性程序；
- LLM 输出一律为 JSON Schema 强校验的结构化对象，**不产生自由文本指令**。

### 4.2 组件架构

```
┌─────────────────────────────────────────────────────────────┐
│ TCEA Orchestrator（状态机引擎，确定性）                          │
│                                                              │
│  ┌──────────┐  ┌──────────────┐  ┌───────────────┐           │
│  │ Monitor   │→│ Diagnoser     │→│ Planner        │           │
│  │ 漂移监控   │  │ (LLM Agent)  │  │ (LLM Agent)   │           │
│  │ 确定性     │  │ 归因推理      │  │ 修复方案规划    │           │
│  └──────────┘  └──────────────┘  └───────┬───────┘           │
│                                          ↓                   │
│  ┌──────────┐  ┌──────────────┐  ┌───────────────┐           │
│  │ Publisher │←│ Validator     │←│ Executor       │           │
│  │ 金丝雀发布 │  │ 孪生回归测试   │  │ 工具执行器      │           │
│  │ 确定性     │  │ 确定性        │  │ 确定性          │           │
│  └──────────┘  └──────────────┘  └───────────────┘           │
│                                                              │
│  横切组件：Memory（案例库/归因知识库） · Audit Log · 人工升级通道  │
└─────────────────────────────────────────────────────────────┘
```

| 组件 | 类型 | 职责 |
|---|---|---|
| **Monitor** | 确定性服务 | 滚动计算分区误差指标（预测 vs 实测回流），触发漂移事件 |
| **Diagnoser** | LLM Agent | 调用诊断工具集，输出带证据链的根因假设（结构化） |
| **Planner** | LLM Agent | 把根因假设映射为修复动作 DAG，估算代价，选最小代价方案 |
| **Executor** | 确定性服务 | 按 DAG 调度执行：仿真生成、训练任务、采集工单 |
| **Validator** | 确定性服务 | 冻结回归测试集 + 影子对比评估，输出通过/不通过 |
| **Publisher** | 确定性服务 | 金丝雀发布（分区灰度）、置信度广播、自动回滚 |
| **Memory** | 向量库 + 结构化库 | 历史案例（漂移→归因→修复→效果），供 Diagnoser 少样本检索 |

### 4.3 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| LLM 介入范围 | 仅归因与规划两个节点 | 这两步需要跨证据推理；其余步骤确定性程序更可靠 |
| 归因输出形式 | 假设列表 + 置信度 + 验证实验建议 | 允许"先做廉价验证实验再下结论"（如先重采 10 个点排除测量噪声） |
| 训练触发粒度 | 空间分区级增量校准（LoRA/Adapter 式轻量微调） | 避免全量重训；漂移通常是局部的 |
| 案例记忆 | 必备 | 同一城市的漂移模式高度重复（季节性），检索历史案例可大幅提升归因准确率 |
| 人工升级 | 置信度 < 阈值或动作代价 > 预算时强制升级 | Agent 解决 80% 常规案例，疑难升级专家 |

## 5. 工具清单（Tool Registry）

Diagnoser / Planner 可调用的工具（全部为幂等只读或沙箱内写操作）：

| 工具名 | 输入 → 输出 | 用途 |
|---|---|---|
| `query_error_stats` | 分区/频段/时段筛选 → 误差统计（RMSE、bias、分布漂移 PSI） | 漂移定界 |
| `query_measurement_quality` | 分区 → 回流数据质量报告（样本量、GPS 精度、设备类型分布） | 排除数据质量根因 |
| `diff_network_config` | 时间窗 → 基站工参变更记录 diff | 排查工参变更根因 |
| `diff_geo_environment` | 分区 → 3D 模型 vs 最新影像/测绘的变化检测结果 | 排查新建筑/植被根因 |
| `query_case_memory` | 当前漂移特征向量 → Top-K 相似历史案例 | 少样本归因参考 |
| `run_probe_simulation` | 分区 + 假设参数 → Sionna RT 小规模探针仿真结果 | 验证"如果是 X 原因，仿真应呈现 Y 误差模式" |
| `mine_bad_cases` | 时间窗 + 阈值 → 聚类后的坏例集合（轨迹/干扰预测严重失误场景） | 坏例挖掘与回灌 |
| `estimate_action_cost` | 修复动作 → 代价估算（GPU 时、采集架次、预计耗时） | 规划阶段选最小代价方案 |
| `create_collection_task` | 分区 + 采样规格 → 采集任务工单（草稿，待人工审批） | 定向补采 |
| `launch_sim_generation` | 分区 + 场景参数 → 仿真数据生成任务句柄 | 定向重跑射线追踪 |
| `launch_calibration_training` | 数据集 + 分区 + 训练配置模板 ID → 训练任务句柄 | 增量校准（仅允许预注册的配置模板） |
| `run_regression_eval` | 模型版本 → 冻结测试集 + 影子对比指标 | 验证 |
| `publish_canary` / `rollback` | 模型版本 + 分区列表 → 发布/回滚操作句柄 | 发布（需通过 Validator 门禁） |
| `broadcast_confidence` | 分区置信度映射表 → 下游通知 | 置信度广播 |

## 6. 核心工作流

### 6.1 主闭环（漂移修复）

```
1. Monitor 检测到分区 Z 干扰图 RMSE 从 4.8dB 漂移至 9.2dB（持续 3 个监控窗）
   → 创建 DriftEvent#123，唤醒 Diagnoser

2. Diagnoser（LLM ReAct，≤15 步工具调用预算）：
   a. query_error_stats        → 误差集中在 Z 区 60–120m 高度层、bias 为正（实测比预测差）
   b. query_measurement_quality → 回流样本量充足、设备分布正常 → 排除数据质量
   c. diff_network_config       → Z 区两站于 5 日前调整下倾角 → 候选根因 A（置信 0.55）
   d. diff_geo_environment      → Z 区检测到新建塔吊群 → 候选根因 B（置信 0.35）
   e. query_case_memory         → 历史案例#87：同类下倾角变更产生相同误差签名
   f. run_probe_simulation      → 用新工参重跑探针仿真，误差模式与实测吻合度 0.91
   → 输出归因报告：根因 = 工参变更（置信 0.88），证据链 6 条

3. Planner（LLM，输出动作 DAG）：
   方案甲：仅更新孪生工参 + Z 区定向重生成仿真数据 + 增量校准（代价：8 GPU 时，无采集）
   方案乙：方案甲 + 30 点定向实测验证（代价：+1 采集架次）
   → 估算后选甲，附带条件：若验证不过则自动升级到乙

4. Executor：更新孪生工参 → launch_sim_generation(Z区) → launch_calibration_training(LoRA 增量)

5. Validator：冻结测试集 RMSE 4.9dB（达标 ≤6dB）；
   非漂移分区指标变化 < 0.2dB（无灾难性遗忘）；影子对比 48h 通过

6. Publisher：Z 区金丝雀发布（10% 流量 24h → 100%）；
   broadcast_confidence 更新 Z 区置信度 0.6 → 0.9

7. 写入 Memory 案例库 + 生成审计报告 → 闭环结束（端到端 < 72h，其中人工介入 0 次）
```

### 6.2 坏例挖掘回灌（周期性子工作流）

```
mine_bad_cases（周级）→ 聚类（如"楼宇峡谷内低速悬停机的轨迹预测系统性偏差"）
→ Diagnoser 判定：模型盲区（训练分布外）
→ Planner：定向仿真生成该模式 5k 样本 + 加权回灌训练
→ Validator 验证该簇 minADE 改善且总体不退化 → 发布
```

### 6.3 主动探测（置信度驱动的廉价巡检）

对长期无实测回流的分区（置信度自然衰减），Agent 主动生成低成本探测建议：将"顺路采集"附加到已报备的物流航线（向 UTM 提交顺路测量请求工单），实现接近零边际成本的持续数据回流。

## 7. 状态机与触发机制

```
IDLE ──(漂移事件/周期任务/人工触发)──▶ DIAGNOSING
DIAGNOSING ──归因置信≥0.7──▶ PLANNING
DIAGNOSING ──归因置信<0.7 或工具预算耗尽──▶ ESCALATED（人工）
PLANNING ──方案代价≤预算──▶ EXECUTING
PLANNING ──方案代价>预算──▶ ESCALATED
EXECUTING ──全部任务完成──▶ VALIDATING
EXECUTING ──任务失败重试2次仍失败──▶ ESCALATED
VALIDATING ──门禁通过──▶ PUBLISHING
VALIDATING ──未通过──▶ PLANNING（携带失败上下文，最多回炉 2 次）──仍失败──▶ ESCALATED
PUBLISHING ──金丝雀达标──▶ DONE（写 Memory + 报告）
PUBLISHING ──金丝雀异常──▶ 自动 rollback ──▶ ESCALATED
任意状态 ──人工中止──▶ ABORTED（自动回滚未发布变更）
```

**触发器**：
- 事件触发：Monitor 的 CUSUM/Page-Hinkley 漂移检验连续 N 窗显著；
- 周期触发：坏例挖掘（周）、全域健康巡检（日）；
- 外部触发：工参变更通知、新 3D 测绘数据到达、人工指令。

**并发控制**：同一空间分区同时只允许一个活跃闭环实例；全局并发训练任务数受配额限制。

| 实测回流流 | MDT 测量、无人机遥测 RSRP/SINR、频谱监测 | Kafka topic，Avro schema |

| 接口 | 内容 | 消费方 |
|---|---|---|
| `ConfidenceMap` | 分区 × 模型 × 置信度等级（含生效时间） | L1 预测服务（调整输出方差）、L2 决策层（调整保守度系数）、L3 意图层（报告） |
| `ModelRelease` | 模型版本、适用分区、验证报告摘要 | 模型注册中心 |
| `CollectionTaskDraft` | 定向采集工单草稿 | UTM/运维审批系统 |
| `AuditReport` | 漂移→归因→动作→验证全链路结构化报告 | 审计库 + 人类运维 |

## 9. Guardrails 与权限边界

| # | 规则 | 实现 |
|---|---|---|
| GR1 | Agent 不可直接发布模型——必须经 Validator 门禁（冻结测试集 + 无遗忘检查 + 影子对比） | Publisher 校验 Validator 签名 |
| GR2 | Agent 不可直接调度无人机——采集任务只生成草稿工单，人工/UTM 审批后执行 | 工具层权限隔离 |
| GR3 | 训练只能使用预注册配置模板（防止 LLM 生成危险超参/任意代码） | `launch_calibration_training` 白名单校验 |
| GR4 | LLM 节点工具调用预算上限（Diagnoser ≤15 步，Planner ≤8 步），超限强制升级人工 | Orchestrator 计数器 |
| GR5 | 资源预算硬顶（GPU 时/采集架次/周），超预算方案必须人工批准 | Planner 输出过预算校验器 |
| GR6 | 所有 LLM 输出过 JSON Schema 校验，失败重试 2 次后升级 | 结构化输出层 |
| GR7 | 金丝雀期间下游关键指标（L2 约束违规率）异常立即自动回滚 | Publisher 监控钩子 |
| GR8 | 全链路审计日志不可篡改，支持闭环回放 | append-only 审计库 |

## 10. 评估指标与验收标准

### 10.1 Agent 自身能力指标

| 指标 | 定义 | 验收线（v1） |
|---|---|---|
| 漂移检测召回率 / 误报率 | 注入式漂移实验（人为改孪生工参/环境后看是否被发现） | 召回 ≥90%，误报 ≤1 次/周 |
| 归因准确率 | 注入已知根因的测试集（≥50 例，覆盖 5 类根因） | Top-1 ≥75%，Top-2 ≥90% |
| 闭环端到端时延 | 漂移发生 → 修复发布 | 中位数 ≤72h（基线人工流程：2–4 周） |
| 自主闭环率 | 无人工介入完成的闭环占比 | ≥60%（v1），≥80%（v2） |
| 修复有效率 | 发布后该分区误差回到达标线的比例 | ≥85% |
| 无回归保证 | 修复导致其他分区/指标退化的事故数 | 0（由 GR1 门禁保证） |

### 10.2 对系统整体的提升指标（North Star）

| 指标 | 基线（人工阶段性校准） | 目标 |
|---|---|---|
| 全域干扰图 RMSE 的**时间加权均值**（含漂移窗口期） | 漂移期可退化至 >9dB，年均约 6–7dB | 全年稳定 ≤5.5dB |
| 漂移暴露时长（误差超标分区·小时数） | 周级 × 多分区 | 下降 ≥70% |
| 校准人力投入 | 专家全程驱动 | 仅处理升级案例（≤40%→≤20%） |
| 下游收益 | — | L2 约束违规率在环境变化期不出现尖峰；管控围栏假阳性（过保守圈禁空域）面积下降 |

### 10.3 评估方法

1. **注入式漂移基准（核心创新评估手段）**：在数字孪生中构建"漂移场景库"（工参变更 / 新建筑 / 季节植被 / 测量噪声 / 新机型，各 ≥10 例），对 Agent 做端到端考试——这本身可发展为可复用的 benchmark；
2. **历史回放**：用试点期积累的真实漂移事件回放对比"Agent 决策 vs 当时专家决策"；
3. **消融**：去掉 Memory 案例库 / 去掉探针仿真工具 / 用固定规则替代 LLM 归因，量化各组件贡献。

## 11. 相对原方案的提升分析

### 11.1 提升的本质

原方案把校准当作**流程中的一个阶段**（8.2 节冷启动策略第 3–4 步）；TCEA 把它升级为**与系统共生的自治回路**。类比：原方案是"定期体检"，TCEA 是"免疫系统"。

### 11.2 量化预期（推导依据）

- AIRMap 已证明"20% 实测校准可把误差从 >50% 降至 ~5%"——说明**校准这件事本身收益巨大且方法成熟**，瓶颈不在算法而在**流程时延**（发现漂移→完成校准的周期）；
- TCEA 攻击的正是流程时延：把"周级人工"压到"小时~天级自主"，因此全域精度的**时间加权均值**改善主要来自漂移暴露窗口的压缩（估计 ≥70% 窗口时长削减）；
- 二阶收益：置信度广播让 L2/L4 在漂移未修复期间自动加大保守度——把"未知的错"变成"已知的不确定"，这是安全性的质变而非量变。

### 11.3 与主方案其他模块的协同

| 模块 | 协同效应 |
|---|---|
| 模块一（轨迹预测） | 坏例挖掘回灌同样适用于轨迹模型；Conformal 校准集由 TCEA 持续更新，保证覆盖率不随分布漂移失效 |
| 模块二（干扰预测） | 直接受益者：底图精度稳定 = 概率热图可信 |
| 模块三（MARL 功控） | 孪生保真度稳定 → Sim2Real 鸿沟收窄 → 策略迁移损失下降；置信度图可作为 MARL 状态输入 |
| 模块四（空域管控） | 干扰围栏假阳性下降 → 空域利用率提升 |
| L3 意图层 | TCEA 报告作为意图层"网络健康度"上下文来源 |

### 11.4 诚实的局限

- 对**突发瞬时漂移**（如临时大型金属结构、突发干扰源）无能为力——闭环最快也是小时级，瞬时问题仍靠 L2 实时层的鲁棒性兜底；
- 归因准确率天花板受工具覆盖度限制（若漂移源不在 5 类根因内，只能升级人工）；
- LLM 归因的收益需对照"规则引擎归因"消融来证明——若试点发现规则可覆盖 90% 案例，应诚实降级 LLM 的角色以省成本。

## 12. 风险与备选方案

| 风险 | 对策 |
|---|---|
| LLM 归因不稳定（同输入不同结论） | 低温采样 + 结构化输出 + 自洽性投票（3 次采样取多数）；Memory 少样本锚定 |
| 增量校准灾难性遗忘 | 分区 LoRA/Adapter 隔离 + 全域冻结回归集门禁（GR1 已覆盖） |
| 探针仿真与现实本身有偏 → 归因被误导 | 探针结论只作为证据之一（权重受置信度封顶），关键归因要求多源证据一致 |
| Agent 频繁触发训练耗尽预算 | GR5 硬预算 + 漂移显著性检验加严（提高触发阈值） |
| 备选方案 A：纯规则引擎（无 LLM） | 作为消融基线必做；若规则覆盖率足够则采纳，LLM 仅处理长尾 |
| 备选方案 B：连续在线学习（无 Agent，模型直接在线更新） | 拒绝——无验证门禁的在线学习在安全关键系统不可接受 |

## 13. 实施清单

按依赖顺序：

- [ ] **P0**：Monitor 服务（误差配对管线 + CUSUM 漂移检验 + 分区聚合）——无 Agent 也独立有价值
- [ ] **P0**：冻结回归测试集 + Validator 门禁 + 模型注册/金丝雀/回滚基建
- [ ] **P1**：工具层实现（`diff_network_config`、`diff_geo_environment`、`run_probe_simulation` 等 14 个工具）
- [ ] **P1**：Diagnoser/Planner LLM 节点 + JSON Schema 输出层 + 工具预算控制
- [ ] **P1**：注入式漂移基准场景库（≥50 例）与评估管线
- [ ] **P2**：Memory 案例库 + 检索增强归因
- [ ] **P2**：置信度广播接口接入 L1/L2 下游
- [ ] **P2**：坏例挖掘子工作流 + 顺路采集工单集成
- [ ] **P3**：消融实验（规则 vs LLM 归因）与试点报告

**最小可行版本（MVP）边界**：P0 + P1 中仅实现"工参变更"和"环境变化"两类根因的归因与修复——这两类在城市场景中占漂移事件的大多数，且工具链最成熟。
